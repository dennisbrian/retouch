## Day 2 — §4 lighting wiring ✅ DONE 2026-07-19 (AB doc, closes a shipped-quality gap)

**Why now:** cheap, isolated, unblocks nothing else but blocks on nothing —
good filler after AC1 while its test runs settle.

- [x] `perf_optimizations.py`'s `sculpt()` call site (in `_process_face_core`,
      shared by both the single-face and pooled multi-face paths — the
      original `perf_optimizations.py:658` line-number citation had drifted,
      re-verified by reading before implementing): sculpt now resolves an
      azimuth/elevation before calling `relighter.sculpt()`.
- [x] **Deviation from the plan, found by reading `relight.py` before
      implementing, not by trusting the doc:** "leave elevation `None`" was
      wrong. `sculpt()` has `if light_azimuth is None or light_elevation is
      None:` — either being `None` re-estimates **both** internally, so
      passing azimuth with elevation=`None` would have silently discarded
      the computed azimuth. Fixed at sculpt's own frontal default (30°)
      whenever a derived azimuth is supplied.
- [x] **Deviation #2, resolved via user clarification rather than guessed:**
      `ctx.relight_azimuth` defaults to `0.0`, not `None` — there is no way
      to distinguish "user left the slider at default" from "user chose
      0°" at the ctx level, so the plan's literal "no explicit azimuth"
      check was unimplementable as written. Resolved: sculpt follows
      `ctx.relight_azimuth`/`elevation` whenever `ctx.relight > 0` (relight
      is actively shading this face — the real signal for "a direction is
      in play"); falls back to the detected key-light direction only when
      relight is off. Also found and fixed: `LightDirection`'s raw 2D
      screen vector `(dx, dy)` is not the same coordinate convention as
      `sculpt()`'s 3D azimuth (z-toward-camera) — a literal `atan2`
      mapping would degenerate to fully-raking ±90° side light for any
      strong catchlight; used a frontal-biased `atan2(dx, 1.0)` damping
      instead, flagged in-code as empirically-tuned and to be verified by
      render, not trusted as a precise coordinate conversion.
- [x] Coherence rule verified: `ctx.relight > 0` is the single gate shared
      by both ops — no path lets them shade in different directions.
- [x] Byte-identical when `light_direction` is unknown **and relight is
      off** — corrected from the plan's unconditional claim (an advisor
      catch: with the relight-active branch now wired, sculpt+relight
      output is *not* byte-identical to before, by design). Both cases
      covered in `tests/test_integration.py::TestSculptLightDirectionWiring`
      (3 tests: relight-active override, relight-off+known, relight-off+
      unknown/byte-identical), all passing against the real engine via
      the `engine` fixture, not mocked at the `Relighter` level.
- [x] Threaded `light_direction` through the full call chain the plan
      didn't anticipate at this depth: `_process_face_core` (new param),
      both its callers (`engine.py`'s direct path, the
      `_process_single_face_worker` `ProcessPoolExecutor` path — new 11th
      tuple element, `LightDirection` confirmed picklable, no session
      objects), and `_process_one_face`'s three call sites (single-face,
      pool-fallback, ThreadPoolExecutor). Computed once per face
      (`all_light_directions`), reused across all branches — no duplicate
      `estimate_light_direction` calls introduced.
- [x] Gating to `source == "catchlight"` only: not applied — `is_known`
      (`confidence > 0 and source != "unknown"`) already covers this
      generically across all three sources (`catchlights`,
      `catchlight_single`, `shading`); a source-specific gate would exclude
      the legitimate lower-confidence shading fallback without a stated
      reason to.

**Unplanned finding, fixed same session (user call: fix now, not deferred):**
sculpt's tests surfaced a pre-existing, unrelated NaN-production bug in both
`relight.py::sculpt()` (line ~536) and `relight.py::relight()`'s v2 engine
(line ~308) — `S_target`/`S_new` normalized via `np.mean(S_target[valid])`
with **no guard** for `valid` being empty (a near-frontal/flat face crop
can leave zero pixels clearing the `N_z < 0.999` grazing-angle threshold).
`np.mean([])` is NaN; dividing by it silently poisons the entire output
canvas with NaN pixels, no exception raised. Confirmed independent of this
week's wiring (reproduces on both the auto-estimate and explicit-azimuth
branches). Fixed by skipping normalization when the valid mask is empty —
the existing downstream gain clip (`[0.7,1.3]` sculpt / `[0.55,1.65]`
relight) already bounds the result safely either way, so this is a pure
guard, not a behavior change on the normal (non-degenerate) path. Two new
regression tests added (`test_sculpt_empty_valid_mask_does_not_produce_nan`,
`test_v2_empty_valid_mask_does_not_produce_nan`), each confirmed to
reproduce the bug via the same arithmetic pattern in isolation before
trusting the fix.

**Exit:** met, plus the NaN fix. A face with a known catchlight-derived
light direction sculpts consistently with its own detected lighting when
relight is off; sculpt follows relight's explicit direction when relight is
active; byte-identical when direction is unknown and relight is off. Full
combined suite (sculpt/relight/lighting/perf_optimizations/engine/
integration): **190 passed, 3 failed** — zero NaN/empty-slice warnings on
any passing test (down from warnings on every sculpt-enabled run before the
fix). The 3 failures are `TestWithRealImage` (`test_detects_face`,
`test_full_pipeline_real_face`, `test_real_face_timings_populated`) —
verified unrelated: `natural_image_path` (`conftest.py`) picks "the first
JPEG alphabetically in `test_output/`", an **untracked, non-deterministic
scratch directory** (not a git fixture — confirmed via `git ls-files`), and
today that resolves to `DSCF4454.jpg`, on which a **fresh, unmodified
`FaceDetector()`** (direct call, zero engine/mocking/session code involved)
detects 0 faces despite the image clearly containing one to a human eye.
`detection.py` has zero diff this session. This is a pre-existing detector-
accuracy edge case (CLAUDE.md's own documented "~4% undetected faces"
limitation) surfaced by fixture non-determinism, not a regression — logged
per owner call, test left as-is, out of Day 2's scope to fix.

**Real-render verification (not simulated — CLAUDE.md Verification &

1's render) through the actual `RetouchEngine` directly, both coherence-rule

- [x] **Core vector implemented 2026-07-20** — `perceived_retouching_vector`

      map; wiring bust/waist/thigh/head/hair labels awaits body reshape joining
      the core engine path. The corpus-calibrated scalar remains intentionally

- [x] Implement the 8-statistic vector: 4 geometric (mean/σ of warp-field
      magnitude **projected onto the local luminance gradient**, over face
      and body separately, body regions weighted per BB's spec:
      bust/waist/thigh ×2, head/hair ×0.5, else ×1) + 4 photometric (mean/σ
      of face-only SSIM on luminance with the brightness term excluded,
      β=γ=1, C₂=0.03², C₃=C₂/2; mean/σ of the 9×9 linear-filter frequency
      response D).
- [x] **Do not ship an SVR** (BB's explicit correction to AA's earlier

- [x] Express the edit cap as a ΔE budget in the oxygenated-blood direction:

- [x] Test: sweep `hb_shift` strength → measured ΔE stays inside the band.

### AA5 teeth (calibrates `teeth_whiten`, also closes BB-F2's sibling gap)
- [x] **WID cap + absolute-gate removal implemented 2026-07-21** — `teeth.py`
      now caps the edit so mean ΔWID over the teeth mask stays inside the
      acceptability band (WAT = 2.62). WID = 0.511·L* − 2.324·a* − 1.100·b*
      (Pérez et al. 2017, CIELAB-based linear form; cleaner than the WIO
      range). Because WID is linear in L*/a*/b*, the cap scales strength
      linearly — no iteration needed. Formula coefficients confirmed verbatim
      from the Pérez 2017 Dental Materials paper (§3 Results).
- [x] Compute a WID delta pre/post whiten; cap so ΔW stays inside the
      acceptability band. Used WID (Pérez 2017) over WIO (Luo 2009) because
      WID is pure-CIELAB and linear (no XYZ→chromaticity conversion, no
      iteration); WPT 0.72 / WAT 2.62 are the cleaner single-number
      thresholds per BB §2.
- [x] **WIO formula pinned:** Luo/Westland 2009 paper (§2.3 eq. 6) gives
      `WIO = Y + 1075.012·(xₙ−x) + 145.516·(yₙ−y)`; Pérez 2017 Table 1
      confirms both WIC and WIO forms verbatim. Not used in the cap (WID is
      cleaner) but recorded here so the "one more fetch" blocker is closed.
- [x] Fold in BB-F2 while touching this function: dropped the redundant
      absolute `l_channel > 80` floor in `teeth.py:121`. Verified it is NOT
      redundant in the mathematical sense — for low-lit mouths (l_median ≈ 60),
      `l_median * 0.9 = 54` admits pixels at L=65 that `l > 80` rejects. The
      absolute gate is a fairness-rule violation (CLAUDE.md Tone-Invariance:
      no absolute intensity thresholds on signals that scale with skin tone).
      Replaced with `l > l_median` (strictly above mouth median) — tone-
      adaptive, rejects both dark voids and uniform images, and detects teeth
      in low-key mouths the absolute gate would have missed. Three new
      regression tests cover the cap, the low-strength path, and the
      dark-mouth detection case.

### AA5 sclera (pairs with the already-shipped BB-F1 fix)
- [x] Completed 2026-07-20 — `_enhance_whites` now pulls red/yellow excess
      toward the subject's own sclera chroma axis first, then brightens only
      toward that sclera's existing 90th-percentile L target. `tests/test_eyes.py`:
      30 passed. Real CLI render on `DSCF7204.jpg` reviewed side-by-side:
      eye whites remain natural with no clipping, gray cast, or display-white
      fabrication.
- [x] Same function as BB-F1 (`_enhance_whites`) — add the de-yellow-first
      (b* toward the face's own axis), brighten-second target, both
      bounded, on top of the already-shipped soft ramp. Never "super-white
      = healthier" — brightening past the natural cap only reads as
      younger, not healthier, per Provine/Russell; don't let the op imply
      otherwise via strength scaling alone.
- [x] Test: same Z0-style gates as the rest of this pack (no mutation,
      resolution stability, confidence on thin masks); monotone in the
      paired metric; bounded delta from input.
