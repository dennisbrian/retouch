## Reconciliation: ask → current state → real gap

### 1. Semantic face understanding / dense parsing / landmark refinement
**Already built:** BiSeNet 19-class semantic parsing + MediaPipe 478-point landmarks (`retouch/parsing.py`), iris/sclera sub-region derivation (see `PHOTOSHOP_PARITY_ROADMAP.md` §7 follow-up, resolved 2026-07-15). **Gap:** hard-argmax BiSeNet masks discard soft probability (Tier C item C3, already in Fable's hardest tier) — this is the actual open item, not a from-scratch build.

### 2. Intrinsic image decomposition / skin reflectance / illumination reconstruction
**Already built:** `retouch/intrinsic.py` (`decompose_intrinsic` — albedo × shading, per MASTER_PLAN R9), `decompose_chromophores` (melanin/hemoglobin, R7). **Gap:** R9 albedo decomposition doesn't yet separate makeup as its own layer — this **is** exactly the P4 makeup-unmix ill-posed problem already ranked #1 in Fable's hardest tier. No new item needed; this vision ask confirms P4's priority rather than adding a new one.

### 3. Physically informed skin reconstruction (pores/wrinkles/acne/freckles/pigmentation/oil/specular/makeup separation)
**Already built:** frequency separation (`retouch/frequency.py`, 3-band), per-region wrinkle/freckle/blemish handling (`PLAN_FRECKLE_BEAUTY_MARK.md` — freckle protect/mole mask shipped per recent commit `f5da97d`), chromophore decomposition (melanin/hemoglobin, R7). **Gap:** "automatically determine preserve vs. attenuate vs. enhance per feature" is a real, not-yet-built classifier/policy layer — closest existing analog is `smart_default.py` (auto-parameter selection) but it doesn't yet operate per-blemish-type with confidence scores. **New candidate item** (see below, tentatively P2/P3 — not yet as hard as P4, no ill-posedness, more a classification+policy engineering task).

### 4. Facial harmony engine (joint optimization across regions, prevent inconsistent adjacent enhancement)
**Partially built:** each region (skin/eyes/lips/brows/hair) is processed with its own masks and the composite path exists, but there's no explicit **joint harmony objective** — no cross-region consistency check comparing e.g. eye enhancement strength vs. skin smoothing strength. **Gap confirmed real** — see `RESEARCH_PER_FACE_AND_P4.md`'s own "B-lite reshape" and per-face slice work touches this partially but doesn't unify it. Flag as new research item, not urgent (P3-tier, greenfield).

### 5. Cross-face consistency in group photos
**Already built:** per-face processing loop with ThreadPoolExecutor (CLAUDE.md architecture), per-face recipe slices (MASTER_PLAN "per-face recipe: engine+CLI+GUI picker shipped"). **Gap:** `style_ref` only applies to the largest face in group shots (B7, already in Fable's hardest tier #5) — again, this vision ask confirms an existing item rather than adding a new one.

### 6. Lighting-aware retouching (illumination/shadow/color-temp/rim/bounce/highlight-rolloff adaptive enhancement)
**Already built:** virtual studio relighting stage, `body_relight.py`, white-balance/color-temp handling. **Gap:** current WB uses hardcoded fudge factors in gamma-encoded LAB rather than a proper Planckian-locus model in linear RGB — this is Tier C item C1, already in Fable's hardest tier. Confirms existing item, no new work needed here.

### 7. Artifact detection and self-correction framework
**Already built — more complete than the vision prompt assumes:** `retouch/qa_detectors.py` already implements `detect_banding`, `detect_clipping`, `detect_plastic_skin`, `detect_halo`, `detect_seam`, `detect_color_drift` (ΔE2000), `detect_pore_spectrum_distance`, `detect_over_retouch_asymmetry`, plus `qa_backoff.py`'s `QABackoff` class for automatic recovery. **Gap:** verify these are wired into the *default* production path and not just available as opt-in/test-only utilities (same "shipped but unreachable" bug class already found in the P0 registry issue) — **this needs a direct verification pass before assuming coverage, per the DONE-means-tests-not-wired lesson.** Flagged as a concrete, cheap next step (see below).

### 8. Modular recipe architecture (reusable graphs, inheritance, conditional execution, hardware-aware scheduling)
**Already built:** recipe JSON system with `extends` parameter inheritance (CLAUDE.md, "25+ recipes... shareable, inheritable"), plugin/marketplace API (T4, MASTER_PLAN confirms done). **Gap:** "confidence-based stage skipping" and "hardware-aware scheduling" are not confirmed present — worth a quick grep-check, likely genuinely absent, but low priority (perf optimization, not correctness).

### 9. Evaluation metrics + automated regression testing preventing quality regressions
**Partially built:** 3,630 tests collected, SSIM-style regression testing mentioned for float32 migration plan, `qa_detectors.py` scoring functions (`gui_skin_score`). **Gap:** "photographer preference prediction" and "aesthetic quality estimation" as trained/learned metrics don't exist — this would require a labeled dataset and model, out of scope without real data (parked, same reasoning as A1/A2 competitor-benchmarking track — licensing/data-acquisition gated).

### 10. Continuous self-improving research framework (auto-discovers weaknesses, generates edge cases, ablation studies)
**Not built, and correctly so for now:** this is meta-infrastructure (an agent that researches the researchers) — legitimately greenfield but also the lowest-leverage item here relative to effort. No existing scaffold. Recommend leaving this unscoped/parked until the concrete gaps above are closed — building a self-improvement framework before the base engine's known gaps (P4, F1, registry bug) are fixed would be solving a meta-problem before the object-level problem.

## S-tier — research frontier (genuinely open-ended, no known optimal solution)

**Distinct category from everything above.** The reconciliation section above maps asks to concrete, scoped gaps in existing code — hard engineering, but solvable with known techniques (classical solvers, careful refactors, GUI wiring). The items below are different in kind: each is a real open research question with no established correct answer, sitting *above* even P4 (currently Fable's #1 hardest item) in difficulty. P4 (skin/makeup unmix) is actually a specific, narrower instance of **S13** below — this tier subsumes and generalizes it.

**"Build X" vs. "Invent X":** everything in the reconciliation section above is a *build* problem — a known technique applied to a known gap (wire the QA detectors, complete the float32 conversion, add a classifier). Every item below is an *invent* problem — there is no reference implementation, no accepted correct method, and "pass the tests" cannot be the success criterion because the tests themselves would need to be invented too. A build task's failure mode is "didn't finish"; an invent task's valid outcome can be "tried a real approach, got a negative result, documented why" — that's not failure, that's the actual output of research. Route accordingly: an agent handed one of these should not be graded on "did it ship," but on "did it produce a real attempt, a measurable partial result, or a rigorous account of why the approach doesn't work."

**How to use this section:** these are not scoped tasks to hand Fable expecting a deliverable. They're a research-direction menu — pick at most one, expect it to take actual research time (weeks-months), and expect partial/negative results to be a valid outcome, not a failure. Do not treat any of these as gated behind "finish P4/F1/registry-bug first" — they're a different track (long-horizon research vs. near-term engineering), and could run in parallel with a research-focused agent while Fable/Haiku handle the concrete tiers above.

### S-tier (research-frontier, pick at most one)
- **S1 — Spectral skin reflectance reconstruction.** *Build version (already exists):* `retouch/intrinsic.py`'s `decompose_chromophores` (R7) — a 2-channel melanin/hemoglobin split, calibrated heuristically. *Invent version:* estimate melanin, hemoglobin, bilirubin, carotene, collagen density, hydration, oil-film thickness, SSS coefficient, epidermis thickness, dermis thickness — ~10 channels — from one JPEG, with **no ground-truth dataset to calibrate against**. The invent-level question isn't "implement the 10-channel model," it's "what training signal or physical constraint could possibly pin down 10 unknowns from 3 RGB values with no ground truth" — that question itself doesn't have a known answer yet.
- **S2 — Identity-constrained generative reconstruction.** *Build version:* diffusion inpainting / denoising (plausible-looking fill). *Invent version:* reconstruct hidden texture, clipped highlights, sensor noise, and JPEG damage while being provably identity-exact (pore positions, mole positions, wrinkle topology, asymmetry, age all unchanged) — not just perceptually plausible. No known method distinguishes "identity-preserving" from "identity-plausible" at this level; that distinction is itself unsolved.
- **S3 — Universal face prior / manifold projection.** *Invent version only, no build analog exists in this codebase:* a "Human Face Space" manifold spanning identity × lighting × makeup × age × ethnicity, with any input face projected to its nearest optimal-restoration point *without* identity drift. Blocked on data acquisition (same gate as A1/A2) — but even with unlimited data, "project without drift" has no established formalization of what "without drift" means mathematically.
- **S4 — Photographer intent inference from pixels only.** *Build version:* `smart_default.py`'s heuristic auto-parameter selection (already exists, rule-based). *Invent version:* classify shoot intent (fashion/cosplay/wedding/beauty/editorial/documentary/magazine/commercial/cinematic) from pixels alone, no metadata, no prompt — an unsolved classification problem because "intent" isn't a property with a stable visual signature; two images with identical pixels-of-interest can carry different intents depending on things a single frame cannot show.
- **S5 — Retouch explainability engine.** No build analog exists. Every edited pixel must answer: which stage touched it, what decision was made, what confidence, what evidence, what expected visual improvement. This is closer to an open problem in interpretable ML applied to image pipelines than a to-do item — "expected visual improvement" as a per-pixel quantity has no accepted definition yet.
- **S6 — Learned human taste model (RLHF for retouching).** *Invent version only.* Replace pixel-accuracy objectives (PSNR/SSIM) with a model of human preference, trained on millions of A/B comparisons, differentiably optimized against. Blocked on data acquisition at the scale RLHF needs — and even with data, "portrait beauty preference" is far noisier/more contested a label than the text-preference data RLHF was built for, so the technique's transfer to this domain is itself unproven.
- **S7 — Automatic artifact discovery (self-expanding QA).** *Build version (already exists, verified live):* `qa_detectors.py`'s fixed detector list (banding/halo/plastic-skin/seam/color-drift/pore-spectrum/asymmetry) plus `QABackoff`. *Invent version:* cluster failure cases at scale to discover artifact families nobody has named yet, then auto-generate a detector *and* a fix for each — the hard part isn't the clustering, it's that "is this cluster a genuine new artifact class or just noise" has no principled test.
- **S8 — Universal lighting canonicalization.** *Build version:* the existing relight stage (`body_relight.py`), which works from estimated but not fully inverse-rendered lighting. *Invent version:* full HDRI environment recovery (sun direction, indoor lights, reflectors, ambient bounce, camera response, lens flare, sensor response) from one JPEG — a harder, more complete inverse-rendering problem than any single published method currently solves outdoors-to-indoors-to-mixed generally.
- **S9 — Personalized beauty model.** No build analog — and no invent-level "solution" is even well-posed, which is what makes this different from S1-S8. Same image, different correct edit depending on viewer/culture/era/photographer-style/brand/client: there is no ground truth to converge toward, only "correct for whom." Success here means building a *policy space*, not finding *the* answer.
- **S10 — Differentiable end-to-end pipeline.** *Build version:* the current stage-by-stage pipeline (segmentation → masks → frequency separation → geometry → skin → grade → sharpen → QA), each independently tuned. *Invent version:* make the entire graph differentiable and optimize it jointly against one global loss — very few commercial pipelines attempt this because most stages (segmentation argmax, geometry warps, QA backoff) are not naturally differentiable; making them so without destroying their current correctness is itself the open research question.

### SSS-tier (near-PhD-level, even further out)
- **S11 — Skin aging time-reversal:** decompose true-skin vs. age-process vs. temporary damage (UV/hydration/elasticity), selectively reverse only temporary aging. Requires a biological aging model with no ground truth — "temporary vs. permanent" itself has no clean biological boundary at the pixel level.
- **S12 — Single-image full 3D face material capture:** recover geometry/normals/roughness/specular/SSS/albedo/displacement/micro-normal maps from one portrait — game-engine-quality material assets from a single JPEG. Adjacent to but far beyond current landmark/geometry work (`geometry.py:FaceReshaper`), which only recovers 2D landmark positions, not material properties.
- **S13 — Differentiable makeup decomposition (full cosmetic-layer stack).** *Build version (already exists, shipped):* P4 (`retouch/makeup_unmix.py`) — a single-layer skin/makeup-α solve, ranked #1 in `FABLE_TASK_LIST_2026_07_15.md`'s hardest tier. *Invent version:* decompose foundation, concealer, powder, blush, bronzer, contour, highlighter, eyeshadow, eyeliner, mascara, lipstick, gloss, and eyebrow product as N *separately editable* layers instead of P4's single α-blend. Same ill-posedness class as P4 (per-pixel underdetermined) but multiplied by N unknowns instead of 1 — genuinely the generalization, not a separate problem. **Recommend treating P4 as the tractable stepping-stone toward S13**, and using whatever constraint strategy eventually works for P4's single layer as the starting hypothesis for S13's N layers.
- **S14 — Human visual system simulator:** simulate retina → optic nerve → contrast sensitivity → color adaptation → visual attention → face recognition, and optimize for perceived quality instead of pixel metrics. No existing scaffold in this codebase; adjacent to vision-science research, not image engineering.
- **S15 — Fully self-optimizing retouch engine:** closed-loop system that generates synthetic hard cases, invents new algorithms, benchmarks them, detects regressions, proposes architecture changes, and keeps only statistically-validated improvements. Already flagged as parked in the reconciliation section above (item 10) under a narrower framing; S15 is the fully-specified version. Correctly lowest-priority in the whole S/SSS tier: building a system that invents solutions to S1-S14 before any human-led attempt at S1-S14 exists would be solving the meta-problem before there's an object-level problem to meta-solve.
- **S16 — Universal portrait foundation model.** *No build analog exists — this is the unifying frame all of S1-S15 point toward.* Instead of dozens of handcrafted modules (segmentation, geometry, skin, makeup, lighting, grade), build one latent portrait representation from which lighting, geometry, skin, makeup, optics, camera response, facial materials, and artistic intent can all be recovered and edited as movements within a single latent space — "one model, not forty modules." This is the most speculative item on the list: it presupposes that S1 (optical properties), S3 (identity manifold), S8 (lighting), and S13 (makeup layers) are all expressible as coordinates in one shared space, which is itself an unproven hypothesis, not an engineering plan. Treat as the eventual unifying question *if and only if* several of S1/S3/S8/S13 individually yield real partial results — attempting S16 directly, with none of its prerequisites solved, would be building a unification of things that don't yet exist.

**Relationship to P4/F1/registry-bug (Fable's current top items):** none of S1-S16 should displace those from the near-term queue. They're a different time horizon (research, months-to-years) vs. near-term engineering (weeks). If a dedicated research track opens up separately from the Fable/Haiku engineering queue, S13 (generalizes P4) and S1 (generalizes the existing chromophore decomposition) are the most natural starting points since they build directly on code that already exists, rather than starting from zero like S3/S6/S9/S14/S15/S16.
